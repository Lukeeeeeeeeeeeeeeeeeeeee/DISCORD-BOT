## 1. Executive Summary

This is a mature, production-grade Discord bot with approximately 1.4M LOC, 157 source files, and 87 test files. The test suite passes 296/296 tests. However, deep engineering analysis reveals significant systemic risks that could cause production failures, data loss, or security vulnerabilities under specific conditions.

**Critical Finding Summary:**
- **3 P0 (Critical)** issues in anti-nuke system that can crash the bot or blind it during attacks
- **1 CRITICAL** database migration bug that causes silent schema drift
- **1 Critical** scheduler week-boundary bug causing wrong-week data processing
- **1 High** recruit flow race condition where leaderboards update after user sees success
- **Multiple** unhandled promise rejections in event handlers
- **Systemic** error-swallowing patterns across 28+ locations in db_async.js

**Overall Assessment:** The bot is functionally mature and well-tested, but has accumulated significant technical debt in error handling, race condition protection, and migration safety. The architecture is generally sound, but several subsystems have hidden failure modes that only emerge under stress (raids, power loss during migration, extended downtime).

## 4. Database Layer Analysis (db_async.js)

**File:** `C:\discord-bot\src\db_async.js` (1276 lines)  
**Severity Distribution:** 1 CRITICAL, 5 HIGH, 7 MEDIUM, 5 LOW

### 4.1 CRITICAL: alter() Helper Swallows ALL Errors

**Location:** Lines 652-658, 1113, 1137  
**Pattern:**
```javascript
const alter = async (sql) => {
  try {
    await db.exec(sql);
  } catch (e) {
    void e;  // Explicitly discards ALL errors
  }
};
```

**Root Cause:** The `void e` anti-pattern intentionally discards the error object. This helper is used for all ALTER TABLE operations in three migrations: `2026-02-06-analytics-day-ts`, `2026-03-02-dm-queue-columns`, and `2026-03-31-dm-claim-id`.

**Consequences:**
- If `ALTER TABLE` fails due to syntax error, missing table, or disk full, the error is silently ignored
- Subsequent backfill queries fail because columns don't exist, but the root cause is hidden
- Schema drift accumulates silently across deployments
- No alerting or logging for DDL failures

**Why It Exists:** Likely added to handle "duplicate column name" errors during idempotency, but over-generalized to catch everything.

**Long-term Impact:** This is the single most dangerous pattern in the database layer. It makes schema migrations non-verifiable and creates invisible data corruption risks.

**Recommended Direction:** Replace with explicit error type checking:
```javascript
const alter = async (sql, context) => {
  try {
    await db.exec(sql);
  } catch (e) {
    if (!e || !String(e.message || '').includes('duplicate column name')) {
      console.error(`[ALTER FAILED] ${context}:`, e);
      throw e;
    }
  }
};
```

**Dependencies:** Interacts with findings 4.2 (backfill failure) and 4.3 (silent error swallowing).

### 4.2 HIGH: 28× void e in Index/Pragma Creation

**Location:** Lines 456-520 (18 occurrences), 532-546 (6 occurrences), 1212-1215 (4 occurrences)

**Pattern:**
```javascript
try {
  await db.exec('CREATE INDEX IF NOT EXISTS idx_xxx ON ...');
} catch (e) {
  void e;  // ALL errors silently discarded
}
```

**Root Cause:** Same anti-pattern as 4.1, applied to index creation. While `IF NOT EXISTS` prevents "already exists" errors, other errors (syntax errors, locked database, permission issues) are silently ignored.

**Consequences:**
- Missing indexes go undetected
- Query performance degrades silently
- `database is locked` errors during concurrent access are masked
- `PRAGMA foreign_keys = ON` failure (db-bootstrap.js:24-40) silently leaves FK constraints disabled

**Why It Exists:** Defensive coding against "index already exists" errors, but incorrectly generalized.

**Long-term Impact:** Foreign key constraints may be disabled, allowing orphaned rows. Missing indexes cause query performance degradation that is invisible until user complaints.

**Recommended Direction:** Standardize on explicit check + specific error catch pattern already used correctly at lines 522-529.

### 4.3 HIGH: Backfill Failure Does Not Block Migration

**Location:** Lines 669-694  
**Pattern:**
```javascript
try {
  await db.exec(`UPDATE analytics_daily_channels SET day_ts = ... WHERE day_ts IS NULL;`);
} catch (e) {
  console.error('Failed to backfill analytics day_ts values', e);
  // No rethrow! Migration marked as applied despite partial data.
}
```

**Root Cause:** Backfill error is logged but swallowed. The migration records itself in `schema_migrations`, so it never runs again, but data is incomplete.

**Consequences:**
- `day_ts` columns may be NULL for historical rows
- Analytics queries relying on `day_ts` may produce incorrect results
- No retry or alerting mechanism

**Why It Exists:** Likely added to prevent migration failure due to pre-existing data issues, but creates silent data gaps.

**Long-term Impact:** Analytics data may be silently corrupted for historical periods. Difficult to diagnose because the migration appears successful.

**Recommended Direction:** Either rethrow after logging (blocking startup until fixed) or implement a separate repair migration that runs independently.

### 4.4 HIGH: Duplicate Schema Definitions (Main Block vs Migrations)

**Location:** Lines 106 vs 1215, 151 vs 1213, 340 vs 1005-1103

**Pattern:** Tables like `multipliers`, `weekly_recruit_overrides`, `dm_campaigns`, etc. are defined in the main schema block AND redefined in migrations or post-migration code. The line 1215 definition is **missing the `guild_id` column**.

**Root Cause:** Schema evolution happened incrementally. The main block was never fully replaced by migrations.

**Consequences:**
- If a table is ever dropped and recreated from the wrong definition, it lacks `guild_id`
- Future schema changes might be applied to one copy but not the other
- Dead code masks the true schema source of truth

**Why It Exists:** Historical accretion — new features added tables in the main block, then migrations were added later without removing the originals.

**Long-term Impact:** Schema drift between code and database. Risk of data loss if wrong definition is used during recovery.

**Recommended Direction:** Single source of truth: main block creates only the absolute minimum (version 0); all changes go through numbered migrations. Remove all table creation from outside the migration system.

### 4.5 HIGH: 26 Redundant ensureColumnWithRetry Calls

**Location:** Lines 1189-1221 (26 call sites)

**Root Cause:** The `ensureColumnWithRetry` pattern was introduced as a defensive migration mechanism for existing databases, but was never removed after the main schema block was updated to include these columns.

**Consequences:**
- 26 unnecessary ALTER TABLE attempts on every startup
- `SQLITE_BUSY` retry logic may trigger under concurrent startup conditions
- Masks the fact that the real migration system should be used instead
- Code clutter obscures actual schema evolution path

**Why It Exists:** Backward compatibility defense that became unnecessary but was never cleaned up.

**Long-term Impact:** Startup performance degradation. False sense of migration safety (developers think columns are being added when they already exist).

**Recommended Direction:** Remove all 26 redundant calls. If backward compatibility with older databases is needed, move these into proper `applyMigration` blocks with version tracking.

### 4.6 MEDIUM: No Recovery from Failed Initialization

**Location:** Lines 1233-1267  
**Pattern:**
```javascript
let dbPromise = null;
let dbInitError = null;

function ensureDbPromise() {
  if (!dbPromise) {
    dbPromise = init().catch((err) => {
      dbInitError = err instanceof Error ? err : new Error(String(err));
      throw dbInitError;
    });
  }
  return dbPromise;
}
```

**Root Cause:** Once `dbPromise` rejects, it stays rejected forever. `close()` attempts to await the rejected promise, which throws, preventing cleanup.

**Consequences:**
- After init failure, database is permanently unavailable until process restart
- `close()` cannot clean up failed connections
- No mechanism to retry initialization after transient failures

**Why It Exists:** Standard promise caching pattern, but missing the reset-on-close logic.

**Long-term Impact:** Any transient DB failure (disk full, locked file) during startup permanently bricks the database connection until process restart.

**Recommended Direction:** In `close()`, check `dbInitError` before awaiting; reset `dbPromise` to `null` on failure to allow retry.

### 4.7 MEDIUM: Relative Database Path

**Location:** Line 11  
**Pattern:** `const DB_PATH = process.env.DATABASE_PATH || './data/recruiter.db';`

**Root Cause:** Relative path resolves against `process.cwd()`, which can vary between development, test runners, and production process managers.

**Consequences:**
- Database file may be created in unexpected locations
- Tests may pollute project root or fail to find DB
- PM2/Docker deployments may resolve to different paths

**Why It Exists:** Convenience for local development, not hardened for production.

**Long-term Impact:** Data loss risk if database is created in a temp directory or container layer that gets destroyed.

**Recommended Direction:** Use `path.resolve(__dirname, '../../data/recruiter.db')` or require absolute path via config.

### 4.8 MEDIUM: Monolithic 1215-Line init() Function

**Location:** Lines 17-1231

**Root Cause:** All schema creation, index creation, migrations, and column additions are crammed into a single async function.

**Consequences:**
- Extremely difficult to navigate or review

**Why It Exists:** Incremental growth without refactoring.

**Long-term Impact:** High risk of introduction of bugs during schema changes. Difficult to audit migration ordering.

### 4.9 MEDIUM: SQL Injection via String Interpolation

**Location:** Lines 36, 762, 1170  
**Pattern:**
```javascript
return await db.all(`PRAGMA table_info(${table})`);
await db.exec(`ALTER TABLE ${table} ADD COLUMN guild_id TEXT`);
await db.exec(`ALTER TABLE ${table} ADD COLUMN ${colDef}`);
```

**Root Cause:** Table and column identifiers are interpolated directly into SQL strings. While currently all values are hardcoded strings within the same file, the pattern is dangerous. `colDef` at line 1170 includes type definitions.

**Consequences:** If table/column names are ever constructed from user input or external configuration, this is a severe SQL injection vulnerability.

**Why It Exists:** SQLite doesn't support parameterized identifiers, so interpolation is common. The risk is the lack of an allowlist.

**Long-term Impact:** Low current risk (all values are hardcoded), but high risk if configuration is ever externalized.

**Recommended Direction:** Use an allowlist for table/column names, or use SQLite's quoting mechanism with strict validation.

### 4.10 MEDIUM: getTableInfo Masks Table-Not-Found Errors

**Location:** Lines 34-40  
**Pattern:**
```javascript
const getTableInfo = async (table) => {
  try {
    return await db.all(`PRAGMA table_info(${table})`);
  } catch (e) {
    return [];  // Masks "no such table" and other errors
  }
};
```

**Root Cause:** Any error (including `SQLITE_ERROR: no such table: xyz`) results in an empty array.

**Consequences:**
- `hasColumn()` returns `false` for non-existent tables (correct by accident)
- `hasCompositePk()` returns `false` for non-existent tables (may cause unnecessary table recreation attempts)
- Real schema corruption is masked

**Why It Exists:** Convenience function that doesn't distinguish error types.

**Long-term Impact:** Schema corruption may go undetected. `hasCompositePk` may attempt to recreate tables that already exist with different schemas.

**Recommended Direction:** Distinguish between "table doesn't exist" (return empty array) and other errors (rethrow).

### 4.11 MEDIUM: db.exec() with Parameters

**Location:** Lines 23-32  
**Pattern:**
```javascript
await db.exec(`
  CREATE TABLE IF NOT EXISTS dm_global_backoff (...);
  INSERT OR IGNORE INTO dm_global_backoff (...) VALUES (1, 0, ?);
`, Date.now());
```

**Root Cause:** `db.exec()` is called with a `?` placeholder and `Date.now()` as parameter. The `sqlite` npm package's `exec()` may or may not support parameterized queries depending on version.

**Consequences:** If params are ignored, `updated_at` becomes NULL, violating `NOT NULL` constraint. Silent data corruption or startup failure depending on driver version.

**Why It Exists:** Likely copied from `db.run()` pattern, but `exec()` doesn't support parameters in all sqlite3 driver versions.

**Long-term Impact:** Startup may fail or create corrupt data depending on driver version.

**Recommended Direction:** Use `db.run()` for parameterized single statements, or inline the timestamp value.

### 4.12 LOW: Integrity Check Non-Fatal by Default

**Location:** db-bootstrap.js lines 42-94

**Root Cause:** Integrity check failures only throw if `DB_INTEGRITY_STRICT=true` is set. By default, failures are logged but startup continues.

**Consequences:** Bot starts with corrupted database; data inconsistencies propagate into business logic.

**Why It Exists:** Availability-over-integrity tradeoff for production.

**Long-term Impact:** Corrupted database may cause subtle logic errors that are difficult to trace back to integrity check failures.

**Recommended Direction:** Make strict mode the default, or at least fail startup for foreign key violations.

### 4.13 LOW: Empty Migration as Version Marker

**Location:** Lines 1223-1226  
**Pattern:**
```javascript
await applyMigration('2026-03-03-protect-points-reset', async () => { });
```

**Root Cause:** An empty migration is used as a sentinel to prevent older code from running a destructive reset.

**Consequences:** Future developers may delete "empty" migrations not understanding their purpose.

**Why It Exists:** Prevents older code paths from executing destructive resets.

**Long-term Impact:** Risk of accidental deletion by future maintainers who don't understand the sentinel pattern.

**Recommended Direction:** Add a comment in the migration registry or use a dedicated `schema_flags` table with a boolean column.

## 5. Scheduler Analysis (scheduler.js)

**File:** `C:\discord-bot\src\scheduler.js` (~963 lines)  
**Severity Distribution:** 1 Critical, 2 High, 4 Medium, 4 Low

### 5.1 Critical: Week Boundary Offset Mismatch (Latent)

**Location:** scheduler.js:710 vs weekly-recalculations.js:66  
**Pattern:**
```javascript
// scheduler.js:710
const weekStart = getWeekStartUtcTs();  // Uses DEFAULT_WEEK_OFFSET_MS (5 min)

// weekly-recalculations.js:66
const weekStart = getWeekStartUtcTs(new Date(Date.now() + WEEK_ROLLOVER_OFFSET_MS));
// WEEK_ROLLOVER_OFFSET_MS = 5 min, cancels out DEFAULT_WEEK_OFFSET_MS
```

**Root Cause:** Two independent constants (`DEFAULT_WEEK_OFFSET_MS` in week.js and `WEEK_ROLLOVER_OFFSET_MS` in weekly-recalculations.js) cancel each other out by coincidence. Currently both call sites return identical values, but if either is modified independently, they silently diverge.

**Consequences:**
- Lock keys and snapshot markers keyed off one `weekStart`
- `weekly_calculations` rows keyed off a different `weekStart`
- Snapshot existence check fails to match stored data
- Repeated catch-up runs or missed catch-ups

**Why It Exists:** Different developers added offset logic at different times without coordinating.

**Long-term Impact:** High maintenance risk. One "fix" to either constant breaks the week boundary alignment, causing data to be written to wrong-week snapshots.

**Recommended Direction:** Remove `WEEK_ROLLOVER_OFFSET_MS` from weekly-recalculations.js since `getWeekStartUtcTs` already handles the boundary. Document the offset behavior in `week.js`.

**Dependencies:** Interacts with scheduler finding 5.2 (startup catch-up) and 5.3 (lock TTL).

### 5.2 High: Startup Catch-Up Only Recovers One Missed Week

**Location:** Lines 760-786  
**Pattern:**
```javascript
const weekStart = getWeekStartUtcTs();
const snapKey = `weekly_snapshot_${weekStart}`;
const existing = await db.get('SELECT key FROM system_events WHERE guild_id = ? AND key = ?', guildId, snapKey);

if (!existing && now >= weekStart && now < weekStart + sanityWindow) {
  await runWeeklyMondayReset(db, client);
}
```

**Root Cause:** The catch-up logic only checks for the current week's snapshot. If the bot was down for multiple consecutive weeks, only the most recent missed week is caught up. Earlier weeks' data is permanently lost.

**Consequences:**
- Extended downtime (>1 week) causes permanent data loss for missed weekly resets
- `weekly_calculations` history has gaps
- Leaderboard data for missed weeks is not reconstructed

**Why It Exists:** Simple implementation that handles the common case (bot down for a few hours/days) but not the edge case (weeks).

**Long-term Impact:** For bots with extended downtime (maintenance, hosting issues), weekly recruiting data has irrecoverable gaps.

**Recommended Direction:** Add a loop that iterates over all missed `weekStart` values between the last snapshot and the current week, running `runWeeklyMondayReset` for each. Cap at a reasonable maximum (e.g., 4 weeks) to prevent runaway catch-up.

### 5.3 High: Lock TTL is 14 Days — Hung Jobs Block for Weeks

**Location:** Line 715  
**Pattern:**
```javascript
const locked = await acquireSchedulerLock(db, {
  guildId,
  key: lockKey,
  ttlMs: 14 * ONE_DAY_MS,  // 14 days
  ...
});
```

**Root Cause:** If the process crashes after acquiring the lock but before writing the snapshot, the lock remains valid for 14 days. During that window, no instance can re-run the reset.

**Consequences:**
- Weekly reset is effectively lost until TTL expires
- Startup catch-up will also fail because it tries to acquire the same lock
- Data inconsistency for the missed week

**Why It Exists:** Conservative TTL chosen to prevent double-runs, but doesn't account for crash scenarios.

**Long-term Impact:** A single crash during Monday reset can cause a week of data to be permanently missed.

**Recommended Direction:** Reduce TTL to 2-3 days (enough to prevent double-runs, but not so long that crashes cause permanent data loss). Add a "force" flag or admin command to clear stale locks.

### 5.4 Medium: Silent Lock Failures Skip Jobs

**Location:** scheduler.js:47-49  
**Pattern:**
```javascript
async function acquireSchedulerLock(db, { guildId, key, ttlMs, scope }) {
  try {
    const locked = await acquireJobLock(db, { guildId, key, ttlMs, failOpen: false });
    if (!locked) debugLog(`Skipped scheduler job due to active lock: ${key}`);
    return locked;
  } catch (error) {
    logUnexpectedError(scope || 'scheduler.lock', error, { guildId, key, ttlMs });
    return false;  // silently skips the job
  }
}
```

**Root Cause:** If `acquireJobLock` throws (e.g., DB connection lost, disk full), the error is caught and `false` is returned. The job is silently skipped with no retry, no alert, and no record.

**Consequences:**
- Maintenance jobs silently don't run
- Weekly resets, daily cleanup, hourly invite cleanup may all be skipped
- No operator visibility into missed maintenance

**Why It Exists:** Fail-closed design to prevent partial maintenance, but lacks observability.

**Long-term Impact:** Silent maintenance failure can lead to data bloat, stale leaderboards, and missed weekly resets without any alert.

**Recommended Direction:** Emit a metric/alert when lock acquisition fails. Consider a dead-letter queue for failed maintenance jobs.

### 5.5 Medium: Double Leaderboard Refresh on Monday Startup

**Location:** Lines 763-764 vs 733-734  
**Pattern:**
```javascript
// Startup IIFE (line 763)
await recomputeLeaderboards(db, guild);

// Inside runWeeklyMondayReset (line 733)
await recomputeLeaderboards(db, guild);
```

**Root Cause:** Startup unconditionally refreshes leaderboards, then if catch-up triggers, `runWeeklyMondayReset` refreshes them again. The `runCoalescedRefresh` mechanism only coalesces concurrent calls, not sequential ones.

**Consequences:**

- Potential rate limit if multiple guilds restart simultaneously

**Why It Exists:** Defensive startup refresh + catch-up logic not coordinated.

**Long-term Impact:** Minor — no data corruption, just wasted resources.

**Recommended Direction:** Check if a refresh was already performed recently before unconditionally refreshing at startup. Or, make the startup refresh conditional on the weekly snapshot not existing.

### 5.8 Low: getWeekStartUtcTs Default Offset is Dead Code

**Location:** week.js:1, 4-8  
**Pattern:**
```javascript
const DEFAULT_WEEK_OFFSET_MS = 5 * 60 * 1000;

function getWeekStartUtcTs(now = new Date(), offsetMs = DEFAULT_WEEK_OFFSET_MS) {
  const date = new Date(now);
  if (Number.isFinite(offsetMs) && offsetMs) {
    date.setTime(date.getTime() - offsetMs);
  }
  // ... compute week start
}
```

**Root Cause:** The 5-minute offset shifts `now` back before computing the day-of-week, but because the function computes `diffToMonday = (day + 6) % 7` and subtracts that many days from midnight UTC, the offset has no effect on the returned weekStart.

**Consequences:** Dead code that is one refactor away from becoming a real bug.

**Why It Exists:** Added for "safety margin" but doesn't actually change the week boundary calculation.

**Long-term Impact:** High maintenance risk. Future developers may "fix" the offset, breaking week boundaries.

**Recommended Direction:** Remove the offset parameter and default. Document that week boundaries are exact midnight UTC Mondays.

### 6.1 P0 Critical: this.client.user.id Null Dereference (11 Locations)

**Location:** Lines 2240, 2283, 2302, 2344, 2380, 252, 268, 1510  
**Pattern:**
```javascript
if (!executor || executor.id === this.client.user.id) return;
```

**Root Cause:** `this.client.user` can be `null` during startup, reconnection, or if the client is not fully ready. Accessing `.id` on `null` throws `TypeError: Cannot read properties of null (reading 'id')`.

**Affected Handlers:**
1. `handleBan` — line 2240
2. `handleChannelDelete` — line 2283
3. `handleRoleDelete` — line 2302
4. `handleMemberAdd` — line 2344
5. `handleWebhookUpdate` — line 2380
6. `handleMemberBanAudit` — line 252
7. `handleMemberKickAudit` — line 268
8. `canActOnMember` — line 1510

**Consequences:**
- Bot crash during startup/reconnect when first event arrives before `client.user` resolves
- During a raid, anti-nuke goes offline precisely when most needed
- Unhandled rejection crashes the process in Node.js strict mode

**Why It Exists:** Defensive coding for `entry.executor` but not for `this.client.user`. The `handleKick` function correctly guards `!executor` before accessing `.id`, but still doesn't guard `this.client.user`.

**Long-term Impact:** Bot is vulnerable to crashes during exactly the scenarios it's designed to protect against (raids, mass bans, channel deletions).

**Recommended Direction:** Create a helper method:
```javascript
getBotUserId() {
  return this.client?.user?.id ?? null;
}
```
Replace all 11 instances of `this.client.user.id` with `this.getBotUserId()`, and short-circuit if it returns null.

**Dependencies:** This is a prerequisite for all anti-nuke functionality. Fixing this enables all other anti-nuke improvements.

### 6.2 P0 Critical: guild Not Validated Before waitForAuditLog

**Location:** Lines 2235-2237, 2278-2280, 2297-2299  
**Pattern:**
```javascript
async handleBan(ban) {
  const guild = ban.guild;
  const entry = await this.waitForAuditLog(guild, AuditLogEvent.MemberBanAdd, ban.user.id);
```

**Root Cause:** `ban.guild`, `channel.guild`, and `role.guild` can be `null` for uncached or partial objects. Passing `null` to `waitForAuditLog` causes `guild.fetchAuditLogs` to throw before the internal try/catch.

**Consequences:**
- Bot crash when processing events for uncached guilds
- Partial channel/role objects from Discord gateway cause null dereference

**Why It Exists:** Assumption that Discord always provides cached guild objects.

**Long-term Impact:** Anti-nuke fails for edge cases (uncached guilds, partial objects).

**Recommended Direction:** Add guard at top of each handler:
```javascript
const guild = ban.guild;
if (!guild || !guild.id) return;
```

### 6.3 P1 High: Unhandled Rejections from Async logAction

**Location:** Line 1756 (trackAction calls logAction without await/catch)  
**Pattern:**
```javascript
// trackAction is synchronous
trackAction(guildId, { ... });

// Inside trackAction:
this.logAction(guildId, { ... });  // async, NOT awaited, NOT caught
```

**Root Cause:** `trackAction` is synchronous but calls `this.logAction()` (async) without `await` or `.catch()`. `logAction` performs multiple async operations (resolveLogChannel, send, fetch user, send DM).

**Consequences:**
- Any failure in the logging path creates an unhandled rejection
- ~20 call sites across the codebase are affected
- Systemic reliability risk

**Why It Exists:** Tracking was designed to be fire-and-forget, but logging has many failure modes.

**Long-term Impact:** Unhandled rejections can crash the process or pollute logs, making real errors harder to find.

**Recommended Direction:** Either make `trackAction` async and `await this.logAction(...)`, or decouple tracking from logging with a queue.

### 6.4 P1 High: Systemic Unhandled Rejections from Event Handlers

**Location:** Lines 946-954  
**Pattern:**
```javascript
this.client.on('guildBanAdd', (ban) => this.handleBan(ban));
this.client.on('guildMemberRemove', (member) => this.handleKick(member));
// ... all handlers are fire-and-forget
```

**Root Cause:** All event handlers are async and invoked without `await` and without a `.catch()` wrapper. If any handler throws, it becomes an unhandled promise rejection.

**Consequences:**
- Single unhandled rejection can crash the process in Node.js strict mode
- During a raid, one crash disables all anti-nuke protection

**Why It Exists:** Discord.js event handlers don't automatically catch async errors.

**Long-term Impact:** Bot reliability during high-stress scenarios (raids) is compromised.

**Recommended Direction:** Wrap all event handlers:
```javascript
this.client.on('guildBanAdd', (ban) => {
  this.handleBan(ban).catch(err => console.error('handleBan error:', err));
});
```

### 6.5 P1 High: waitForAuditLog Silently Returns null on Non-Rate-Limit Errors

**Location:** Lines 2186-2191, 2225  
**Pattern:**
```javascript
} catch (error) {
  const retryDelay = this.getRateLimitDelayMs(error);
  if (retryDelay > 0) {
    await this.sleep(retryDelay);
    continue;
  }
  continue;  // Silently swallows non-rate-limit errors
}
```

**Root Cause:** Non-rate-limit errors (e.g., missing `View Audit Log` permission, guild unavailable) are silently dropped via `continue`. All 4 attempts may fail, and the caller receives `null` with no log indication of why.

**Consequences:**
- Missing `View Audit Log` permission goes undetected
- Anti-nuke is completely blind but appears functional
- Debugging requires adding console.log statements

**Why It Exists:** Retry logic focused on rate limits, not permission errors.

**Long-term Impact:** Anti-nuke silently fails for guilds missing audit log permission. Operators see no alerts.

**Recommended Direction:** Log non-rate-limit failures before continuing:
```javascript
console.warn(`Audit log fetch failed for guild ${guild.id}, type ${type}: ${error.message}`);
```

### 6.6 P1 High: Race Condition in processedAuditEntries Deduplication

**Location:** Lines 2204-2216  
**Pattern:**
```javascript
if (this.processedAuditEntries.has(entry.id)) continue;  // check
// ... async yield ...
this.processedAuditEntries.add(entry.id);                 // use
```

**Root Cause:** Because `waitForAuditLog` is async and yields at `await this.sleep(...)` and `await guild.fetchAuditLogs(...)`, two concurrent events can both pass the `has()` check before either reaches `add()`.

**Consequences:**
- Classic TOCTOU race condition
- A single audit log entry could be double-counted
- False positives in anti-nuke detection
- Framing vulnerability (splitting credit for a coordinated attack)

**Why It Exists:** Async/await introduces yield points between check and set.

**Long-term Impact:** Under high concurrent load (raid scenario), audit entries may be double-counted, causing incorrect attribution.

**Recommended Direction:** Use a `Map<entryId, { addedAt: number }>` with atomic check-and-set, or use a `Set` with a per-entry Promise lock.

### 6.8 P2 Medium: Audit Log Fetch Storm Under Concurrent Events

**Location:** Lines 2165+  
**Root Cause:** No global rate limiting or per-guild queue. If 10 channels are deleted at once, 10 concurrent `fetchAuditLogs` calls hit the same guild.

**Consequences:**
- Discord's audit log rate limit (~1 req/sec per guild) is exceeded
- Cascading rate limits cause all audit log fetches to fail
- Anti-nuke goes blind during the storm

**Why It Exists:** No rate limiting architecture in the anti-nuke system.

**Long-term Impact:** During coordinated attacks (mass channel deletion), anti-nuke protection degrades due to rate limits.

**Recommended Direction:** Implement per-guild rate limiting with a queue. Minimum 1000ms spacing between `fetchAuditLogs` calls per guild.

### 6.9 P2 Medium: getRateLimitDelayMs Unit Confusion

**Location:** Lines 1037-1053  
**Pattern:**
```javascript
const retryAfter = Number(retryAfterRaw);
if (Number.isFinite(retryAfter) && retryAfter > 0) {
  return retryAfter > 1000 ? Math.round(retryAfter) : Math.round(retryAfter * 1000);
}
```

**Root Cause:** Discord's `retry_after` for audit logs is typically in milliseconds. Multiplying by 1000 would convert e.g. `500` to `500000` (8+ minutes), which is excessive.

**Consequences:** Overly long sleep times on rate limit, causing delayed retry and potential missed audit log entries.

**Why It Exists:** Uncertainty about whether Discord returns seconds or milliseconds for `retry_after`.

**Long-term Impact:** Anti-nuke response is slower than necessary during rate limit scenarios.

**Recommended Direction:** Clarify the unit, and cap the sleep:
```javascript
const delayMs = Number.isFinite(retryAfter) 
  ? Math.min(retryAfter > 1000 ? retryAfter : retryAfter * 1000, 30000) 
  : 0;
```

## 7. Recruit Flow Analysis

### 7.1 P1 High: Leaderboard Recomputation is Fire-and-Forget

**Location:** src/services/recruiting/recruit-service.js:652-681  
**Pattern:**
```javascript
// In production (NODE_ENV !== 'test'):
recomputeLeaderboards(db, guild).catch(() => {});
recomputeWarningsLeaderboard(db, guild).catch(() => {});
```

**Root Cause:** Leaderboard recomputation is only awaited in test environment. In production, it's fire-and-forget.

**Consequences:**
- User sees "recruit successful" before leaderboards actually update
- Race condition where user checks leaderboard and sees stale data
- If recomputation fails, user has no indication

**Why It Exists:** Likely added to reduce command response latency, but creates user-facing inconsistency.

**Long-term Impact:** Users lose trust in leaderboard accuracy. Support tickets increase.

**Recommended Direction:** Either await leaderboard recomputation (accepting slightly slower response) or return a "processing" indicator and update the message when complete.

## 8. Cross-System Interaction Analysis

### 8.1 Scheduler ↔ Anti-Nuke Interaction

**Finding:** The scheduler's `runWeeklyMondayReset` calls `performWeeklyRecalculations`, which internally calls `handleExpiredAbsences`. `handleExpiredAbsences` sends DMs to staff members. If the anti-nuke system is in a degraded state (e.g., missing audit log permission), the DM sends may still proceed, but the anti-nuke protection for those DM-related actions is absent.

**Risk:** Medium — DM sends are not protected by anti-nuke, but this is by design.

### 8.2 Recruit Flow ↔ Scheduler Interaction

**Finding:** The recruit flow resets weekly points inside `performWeeklyRecalculations` (line 167: `UPDATE recruiters SET points = 0`). This runs inside a per-recruiter transaction. If the scheduler is disabled (finding 5.6), the points reset never happens, causing points to accumulate indefinitely.

**Risk:** High — scheduler disablement causes silent points inflation.

### 8.3 Database Layer ↔ All Systems

**Finding:** The `void e` anti-pattern in db_async.js affects every system that relies on the database. Silent schema drift, missing indexes, and disabled foreign keys propagate silently into all business logic.

**Risk:** Systemic — every subsystem is affected by database layer issues.

### 8.4 Anti-Nuke ↔ Event Handlers Interaction

**Finding:** All event handlers (`guildBanAdd`, `channelDelete`, `roleDelete`, etc.) are registered without error boundaries. If any handler throws (e.g., due to finding 6.1), the entire event emitter chain for that event type is disrupted.

**Risk:** High — a single null dereference disables all protection for that event type.

## 9. Architectural Review

### 9.1 Project Structure

**Strengths:**
- Clear separation: commands, lib, services, scheduler, repos
- Consistent naming conventions
- Service layer abstracts business logic from command handlers

**Weaknesses:**
- `src/lib/antinuke.js` is 4578 lines — a single file with multiple responsibilities
- `src/db_async.js` is 1276 lines — monolithic init function
- `src/scheduler.js` is 963 lines — multiple concerns in one file
- No plugin capability or extension points

### 9.2 Module Boundaries

**Strengths:**
- Repos abstract database access
- Services encapsulate business logic
- Event handlers are separate from commands

**Weaknesses:**
- `antinuke.js` mixes state management, event handling, DM routing, and rollback logic
- `scheduler.js` mixes job scheduling, leaderboard refresh, and maintenance logic
- `recruit.js` command file contains business logic that should be in the service layer

### 9.3 Coupling

**Tight Coupling:**
- `scheduler.js` directly imports and calls `performWeeklyRecalculations` from `weekly-recalculations.js`
- `antinuke.js` directly accesses `this.client` in many places, making it hard to test
- `recruit.js` directly uses `db` instead of going through the service layer

**Loose Coupling:**
- Service layer is well-isolated from Discord.js specifics
- Repos are pure database abstraction

### 9.4 Abstraction Quality

**Strengths:**
- `withTransaction` helper provides consistent transaction semantics
- `runWithConcurrency` provides safe parallel execution
- `acquireJobLock` provides distributed locking

**Weaknesses:**
- `void e` anti-pattern undermines error abstraction
- No consistent retry policy across async operations
- No circuit breaker pattern for external API calls

### 9.5 Dependency Graph

**Concerns:**
- `index.js` imports many subsystems in a flat structure
- `scheduler.js` imports `performWeeklyRecalculations` directly, creating tight coupling
- `antinuke.js` has circular-ish dependencies through `this.client`

**Present:**

**Missing:**

- No retry for `fetchAuditLogs` non-rate-limit errors

### 10.3 Timeout Issues

- No overall request timeout for command handlers

### 10.4 Cancellation Problems

### 10.6 Race Conditions

**Documented:**

### 10.7 Lifecycle Bugs

### 10.8 Memory Leaks

**Low Risk:**

## 18. DM Worker System Analysis

**Files Analyzed:**
- `src/services/dm/dm-worker.js` — Main DM worker, claim/lease management
- `src/services/dm/dm-worker-selector.js` — Worker selection and affinity routing
- `src/services/dm/dm-campaign-service.js` — Campaign creation and target assignment
- `src/services/dm/dm-reporter.js` — Campaign reporting
- `src/services/dm/dm-legacy-command.js` — Legacy DM command
- `src/lib/analytics.js` — Analytics tracking

**Severity Distribution:** 2 P0 (Blocker), 4 P1 (Critical), 7 P2 (Medium), 5 P3 (Low)

### 18.1 P0 — Blocker: Lease Refresher Can Steal Claims From Other Workers

**Location:** `src/services/dm/dm-worker.js` lines 158–164, 596–622

The `leaseRefresher` interval blindly extends `claim_expires_at` without verifying `claim_id` or `assigned_worker_id`. If Worker A crashes and recovers, its refresher can reset the lease on a target that Worker B has already claimed, creating a zombie claim where both workers believe they own the target.

**Root Cause:** `updateTargetStatus` uses `UPDATE ... WHERE id = ?` with no condition on `claim_id`. Any interval referencing this target ID can overwrite another worker's claim lease.

**Consequences:** Targets can be double-sent or stuck in `claimed` state indefinitely.

**Recommended Direction:** Add `AND claim_id = ?` to the UPDATE in `updateTargetStatus`, passing the original claim ID.

---

### 18.2 P0 — Blocker: Memory Leak — leaseRefresher Never Cleared on Early Returns

**Location:** `src/services/dm/dm-worker.js` lines 140–155, 158

When `routeTargetToWorker` returns `'reassigned'` or `'undeliverable_no_worker'`, the function returns at lines 142 or 155 **before** reaching the `try` block where `clearInterval(leaseRefresher)` is called. Each early return leaks one `setInterval` reference that holds references to `targetId` and the entire `DMWorker` instance.

**Consequences:** Memory leak proportional to campaign size. Under sustained load, the worker process will OOM or degrade due to thousands of orphaned intervals firing concurrently.

**Recommended Direction:** Add `clearInterval(leaseRefresher)` before every early return.

---

### 18.3 P1 — Critical: Dual Incompatible Eligible Worker Caches

**Location:** `src/services/dm/dm-worker-selector.js` line 12, 73–95 (60s cache) vs `src/services/dm/dm-worker.js` lines 541–550 (2s cache)

Both modules maintain independent module-scoped caches for the same `dm_workers` table data with different TTLs. Any consumer importing from either module gets a different view of which workers are online.

**Consequences:** Routing decisions are made against stale or divergent worker lists, causing unnecessary reassignments, increased `worker_switches`, and premature `undeliverable` classifications.

**Recommended Direction:** Consolidate into a single exported cache with a single TTL, or document the divergence and ensure all callers use the same module.

---

### 18.4 P1 — Critical: buildTargetAssignments Ignores Campaign-Specific Routing Settings

**Location:** `src/services/dm/dm-campaign-service.js` lines 158, 170

`buildTargetAssignments` hardcodes `stickyWindowMs` to 24 hours and `maxMiscStreak` to 4. But `dm_campaigns` has columns `sticky_window_hours` and `max_misc_streak`, and runtime `routeTargetToWorker` uses the campaign's actual settings.

**Consequences:** Campaigns with non-default routing settings produce incorrect pre-assignments, causing excessive worker reassignments.

**Recommended Direction:** Pass `sticky_window_hours` and `max_misc_streak` from the campaign to `buildTargetAssignments`.

---

### 18.5 P1 — Critical: findPreviouslySentIds Creates DM Channels for Every Member

**Location:** `src/services/dm/dm-legacy-command.js` lines 89–105

For every member in the guild (potentially thousands), this function calls `member.createDM()` and `dm.messages.fetch()`. This creates DM channels on Discord's side and fetches full message history.

**Consequences:** For a guild with 5,000 members, this makes 5,000 sequential API calls taking 16+ minutes. Potential rate-limit bans and TOS violations.

**Recommended Direction:** Replace with a DB-based deduplication query using `dm_delivery_attempts`.

---

### 18.6 P1 — Critical: Campaign Completion Can Be Missed Between Poll Cycles

**Location:** `src/services/dm/dm-worker.js` lines 324–347

`checkCampaignCompletion` is only called for campaigns that had at least one target claimed in the current poll cycle. If a campaign's last remaining targets were processed in a previous cycle and no new targets are claimed now, the campaign status is never transitioned from `'running'` to `'completed'`.

**Consequences:** Campaigns can get stuck in `'running'` state indefinitely, never generating reports.

**Recommended Direction:** Run `checkCampaignCompletion` for all `running` campaigns periodically, not just those with newly claimed targets.

---

### 18.7 P2 — Medium: Claim ID Collision Risk from Insufficient Randomness

**Location:** `src/services/dm/dm-worker.js` line 63

`Math.random().toString(36).slice(2, 7)` produces only 5 base-36 characters (60M possible values). Under high throughput, collision probability becomes non-negligible.

**Recommended Direction:** Use `crypto.randomUUID()` or `crypto.randomBytes(8).toString('hex')`.

---

### 18.8 P2 — Medium: Stale Worker Detection Creates Assignment Thrashing

**Location:** `src/services/dm/dm-worker.js` lines 77–88, 21–23

`ASSIGNMENT_STALE_MS` is 45,000ms (3 heartbeat intervals). Under SQLite load or Node.js event-loop lag, a healthy but slightly delayed worker has its assignments stripped and redistributed, causing assignment thrashing.

**Recommended Direction:** Increase stale threshold to 2-3x heartbeat interval with jitter, or use heartbeat timestamps with grace period.

---

### 18.9 P2 — Medium: Synchronous File I/O in Legacy DM Command

**Location:** `src/services/dm/dm-legacy-command.js` lines 30–42

`readHistory` and `writeHistory` use `fs.readFileSync` and `fs.writeFileSync`, blocking the event loop. For large history files, command latency scales linearly with file size.

**Recommended Direction:** Use async file I/O with atomic writes (write to temp file, rename).

---

### 18.10 P2 — Medium: Missing Composite Index on dm_workers

**Location:** `src/db_async.js` lines 340–349 (schema)

The stale assignment release query filters `dm_workers` by `enabled = 1 AND status = 'online' AND last_seen_at >= ?`. There is no composite index on these columns, causing full table scans under high worker counts.

**Recommended Direction:** Add composite index `CREATE INDEX idx_dm_workers_online ON dm_workers(enabled, status, last_seen_at)`.

---

### 18.11 P2 — Medium: Concurrent Report Posting Can Create Duplicate Embeds

**Location:** `src/services/dm/dm-reporter.js` lines 260–284

`scanAndPostReports` is not atomic. Two concurrent instances can read the same unreported campaign and both post reports.

**Recommended Direction:** Use atomic `UPDATE ... WHERE report_posted = 0 RETURNING` or `SELECT ... FOR UPDATE`.

---

### 18.12 Systemic: Unhandled Promise Rejections in Analytics Flush

**Location:** `src/lib/analytics.js` lines 85, 92, 500

`void flushAll()` and `void flushRoleChanges()` are fire-and-forget async calls. If these reject (e.g., SQLite lock errors), the rejection is unhandled.

**Consequences:** Bot process crash on analytics flush failure in Node.js >= 15 with `--unhandled-rejections` flag.

**Recommended Direction:** Add `.catch(() => {})` or proper error propagation to all `void` calls.

---

### 18.13 Systemic: getEligibleWorkers Export Name Collision

**Location:** `src/services/dm/dm-worker-selector.js` line 12 vs `src/services/dm/dm-worker.js` line 541

Both modules export a function named `getEligibleWorkers` with different implementations, caches, and default parameters.

**Consequences:** Developer confusion, inconsistent routing, potential bugs when new code imports from the "wrong" module.

**Recommended Direction:** Rename one export or consolidate into a shared module.

## 19. Economy & Multiplier System Analysis

**Files Analyzed:**

**Severity Distribution:** 0 P0, 3 P1 (High), 7 P2 (Medium), 8 P3 (Low)

### 19.1 P1 — High: Side-Effectful Read in getActiveMultiplier

**Location:** `src/lib/economy.js` lines 99–143

`getActiveMultiplier` performs a DELETE as a side effect of a read. Every call to "read" the active multiplier triggers a DELETE of expired rows. This is called in 5+ locations (`recruit-service.js:547`, `recruiter-multiplier-service.js:85`, `recruiter-info-service.js:38`, `recruiter.js:189`, `recruiter-buy-service.js:115`).

**Consequences:** Non-atomic delete+select creates a race window. Silent state mutation on read. Not safe for read replicas.

**Recommended Direction:** Move expiration cleanup to a scheduled job or explicit `purgeExpiredMultipliers` function.

---

### 19.2 P1 — High: Race Condition — Multiplier Expires During Recruit Flow

**Location:** `src/services/recruiting/recruit-service.js` lines 547–625

The multiplier is read before any transaction begins, and the points award is in a separate transaction from the recruit insertion. Between reading the multiplier and committing the points, the multiplier could expire.

**Consequences:** User receives points at the old (higher) rate even though the multiplier expired mid-operation.

**Recommended Direction:** Read the multiplier inside the same transaction that awards points, or snapshot the multiplier ID at recruit creation.

---

### 19.3 P1 — High: Raw Transactions in Old recruit.js Command

**Location:** `src/commands/recruiting/recruit.js` lines 558–588

Uses manual `BEGIN TRANSACTION` without retry logic, queuing, or `BEGIN IMMEDIATE`. Compared to `withTransaction` (which uses `BEGIN IMMEDIATE` and retries on `SQLITE_BUSY`):
- No retry on lock contention
- No queuing
- Concurrent recruit commands can corrupt each other

**Consequences:** Transaction failures under concurrent load. DB can be left in inconsistent state.

**Recommended Direction:** Replace raw transaction management with `withTransaction` helper.

---

### 19.4 P1 — High: Duplicate Command Implementations (Old vs New)

**Location:** `src/commands/recruiting/recruit.js` (652 lines, active) vs `src/services/recruiting/recruit-service.js` (826 lines, unused as command)

There are two completely separate implementations of the same recruit flow. The active command uses raw SQL and lacks floor protection on points. The service layer has safer transaction handling and ledger integration.

**Consequences:** Bug fixes applied to one path may not be applied to the other, causing divergent behavior.

**Recommended Direction:** Migrate the active command to use the service layer, or consolidate into a single implementation.

---

### 19.5 P2 — Medium: Duplicate calculateRecruitPoints Implementations

**Location:** `src/lib/economy.js` lines 78–82 vs `src/services/recruiting/rules-service.js` lines 25–34

Two separate implementations with different parameter handling and normalization. The `rules-service.js` version clamps `<=0` multipliers to `1.0`, while `economy.js` does not.

**Consequences:** Behavioral divergence if one is updated and the other is not.

**Recommended Direction:** Single source of truth for points calculation.

### 19.6 P2 — Medium: No Unique Constraint on Active Multipliers

**Location:** `src/db_async.js` lines 106–114

The `multipliers` table has no constraint to prevent multiple active rows of the same type. Duplicate prevention is enforced in application code only.

**Consequences:** Admin could accidentally stack duplicate multipliers.

**Recommended Direction:** Add `UNIQUE(guild_id, recruiter_id, type)` partial index where `expires_at > ?`.

### 19.7 P2 — Medium: Guild-ID Fallback Queries Risk Cross-Guild Leakage

**Location:** `src/lib/economy.js` lines 128–133

Fallback queries omit `guild_id` when the column is missing. If any row has `guild_id = NULL` from a partial migration failure, the fallback query returns it for any guild.

**Consequences:** Multipliers from one guild could be visible to another guild.

**Recommended Direction:** Add `CHECK (guild_id IS NOT NULL)` constraint or ensure all INSERT paths require `guild_id`.

### 19.8 P2 — Medium: Floating-Point Accumulation Drift

**Location:** `src/lib/economy.js` line 81, `src/services/recruiting/ledger-service.js` line 76

Per-recruit rounding to 2 decimal places, but accumulation happens at DB level without re-rounding. Over hundreds of recruits, drift can accumulate.

**Consequences:** Displayed points may not match actual DB value.

**Recommended Direction:** Apply rounding on read/write boundaries.

**Location:** `src/lib/economy.js` lines 99–143

Every call to `getActiveMultiplier` performs a DB round-trip plus a DELETE sweep. No caching layer exists.

**Consequences:** Unnecessary DB load and lock contention during mass-recruit events.

**Recommended Direction:** Add a short-TTL in-memory cache keyed by `(guildId, recruiterId)`.

### 19.10 P2 — Medium: Unbounded Multiplier Row Growth

**Location:** `src/lib/economy.js` lines 153–172

`applyMultiplier` blindly INSERTs without checking for existing active multipliers. Over time, a user could accumulate dozens of expired multiplier rows.

**Consequences:** DB bloat, slower `getActiveMultiplier` scans.

## 20. Index.js Startup Sequence Analysis

**File:** `src/index.js` (1,084 lines) — the actual entry point (index.js at root is a 2-line proxy)

### 20.1 P0 — Critical: AECS Initialization Has No Safety Net

**Location:** `src/index.js` line 67

`AECS.init()` is called synchronously at module load time. If the log directory is unwritable or the dispatcher fails to allocate resources, it throws an uncaught exception before any try/catch exists.

**Consequences:** Process aborts immediately with no graceful shutdown.

**Recommended Direction:** Wrap `AECS.init()` in try/catch or make it tolerate init failures.

---

### 20.2 P1 — High: Anti-Nuke Init Failures Silently Swallowed

**Location:** `src/index.js` lines 105–109

The `.catch()` converts a rejection into a resolved promise. The bot proceeds as if anti-nuke is active, but `runtime.setAntiNuke` receives the uninitialized instance.

**Consequences:** Bot starts without anti-nuke protection. All anti-nuke commands and event handlers become no-ops.

**Recommended Direction:** Make anti-nuke init fatal if it fails, or expose a health check that prevents `onReady` from declaring success.

---

### 20.3 P1 — High: Invite Init Failures Silently Swallowed

**Location:** `src/index.js` lines 111–117

Same pattern as anti-nuke. If invite init fails, the bot starts without invite tracking.

**Consequences:** `/invite` command and join attribution fail silently.

**Recommended Direction:** Same as anti-nuke — either fatal or health-check gated.

---

### 20.4 P1 — High: DB Error Classification Is String-Matching

**Location:** `src/index.js` lines 1072–1076

The catch block only recognizes SQLite errors containing `"database"`. Other fatal DB errors fall through to a generic message.

**Consequences:** Operators receive misleading error messages.

**Recommended Direction:** Check for SQLite error codes (`SQLITE_*`) instead of substring matching.

---

### 20.5 P1 — High: Command Registration Non-Blocking

**Location:** `src/index.js` lines 368–374

Guild-specific command registration is fire-and-forget. If the REST API call fails, the bot starts but slash commands are not available.

**Consequences:** Bot is functionally dead until commands are manually registered.

**Recommended Direction:** Make command registration blocking or add retry logic.

---

### 20.6 P1 — High: onReady Crash Risk

**Location:** `src/index.js` line 406

`client.once('clientReady', onReady)` — `onReady` is async with no error boundary. If any awaited operation throws, the rejection propagates to Node.js as an unhandled rejection.

**Consequences:** A single bug in `onReady` crashes the entire bot.

**Recommended Direction:** Wrap `onReady` body in a generic catch.

---

### 20.7 P2 — Medium: db.close() Timeout Too Short

**Location:** `src/index.js` lines 490–498

A hard 2-second timeout on `db.close()`. SQLite WAL checkpoints on large databases can exceed 2s, causing forced exit before data is flushed.

**Consequences:** Potential data loss on shutdown.

**Recommended Direction:** Increase timeout to 5–10s or make it configurable.

---

### 20.8 P2 — Medium: Token Sanitization Mismatch

**Location:** `src/register-commands.js` lines 292–294 vs `src/index.js` sanitizeEnvToken

`registerCommands` re-reads and re-sanitizes the token instead of reusing the sanitized token from `sanitizeEnvToken()`. If `DISCORD_TOKEN` contains stray quotes or whitespace, the main login succeeds but command registration fails.

**Recommended Direction:** Reuse the sanitized token from `sanitizeEnvToken()`.

---

### 20.9 P2 — Medium: Health Server Stale Metrics

**Location:** `src/index.js` lines 386–404

The health server returns static metrics from `runtime` without refreshing them. Under load, the metrics become stale.

---

### 20.10 P3 — Low: Redundant dotenv Call

**Location:** `src/index.js` line 1

`require('dotenv').config()` is called at the top of `src/index.js`, but the root `index.js` proxy also loads `dotenv` (or it may be loaded elsewhere). This is harmless but redundant.

## 22. AECS Logging/Telemetry System Analysis

**Files Analyzed:**

- `src/lib/aecs/vault.js` (338 lines) — Persistence layer (JSONL + index)

**Severity Distribution:** 1 P0 (Critical), 3 P1 (High), 9 P2 (Medium), 4 P3 (Low)

### 22.1 P0 — Critical: Unbounded Vault Buffer + Total Data Loss on Stream Error

**Location:** `src/lib/aecs/vault.js` lines 25, 86–90, 263–296

The `buffer[]` array has no maximum size. If the flush interval is long or disk I/O stalls, records accumulate with no cap. Additionally, if a stream error fires during the flush loop, `disablePersistence` is called, and the entire buffer is dropped.

**Consequences:** OOM crash under sustained load. Total data loss on any I/O error.

**Recommended Direction:** Add a maximum buffer size with a drop/block policy. Implement partial-flush recovery.

---

### 22.2 P1 — High: Empty handshakeSecret Bypasses Signature Verification

**Location:** `src/lib/aecs/AECS.js` lines 56, 192–205

If `handshakeSecret` is empty/unconfigured, `verifyPayload()` returns `true` for every payload, including tampered ones.

**Consequences:** Any client can forge handshake tokens and inject arbitrary trace contexts, bypassing the entire trace provenance system.

**Recommended Direction:** Start up validation that rejects empty secret, or at minimum log a warning and run in degraded mode.

---

### 22.3 P1 — High: Escalator Errors Silently Swallowed

**Location:** `src/lib/aecs/Dispatcher.js` lines 139–148

If a dictionary-defined `escalator` function throws, the error is completely swallowed (`void error`). The impact silently falls back to `baseImpact`.

**Consequences:** A broken escalator silently downgrades severity. For example, `DB-502` escalator would return 45 instead of 95 for `anti-nuke-purge`, potentially routing a high-impact error to the wrong webhook.

**Recommended Direction:** Log escalator errors and fall back to a safe default impact.

---

### 22.4 P1 — High: dispatch() Unwrapped — Unhandled Rejections

**Location:** `src/lib/aecs/Dispatcher.js` lines 287–359

The entire `dispatch()` body is unwrapped. If `sanitizeMeta` throws due to circular references, or if `CodexError.fromUnknown` throws, the rejection bubbles up to the caller.

**Consequences:** Unhandled promise rejections; telemetry gap during cascading failures.

**Recommended Direction:** Wrap `dispatch()` body in a try/catch.

---

### 22.5 P1 — High: Non-Atomic Initialized Flag Allows Double-Init

**Location:** `src/lib/aecs/AECS.js` lines 95–104

`this.initialized` is a plain boolean. If two concurrent calls reach `init()` before either sets the flag, both will start vault and dispatcher.

**Consequences:** Duplicate timers, duplicate AsyncLocalStorage contexts, potential double-writes to vault.

**Recommended Direction:** Use a state machine (`IDLE | STARTING | RUNNING | STOPPING | STOPPED | ERROR`).

---

### 22.6 P1 — High: reinitialize() Continues After Failed shutdown()

**Location:** `src/lib/aecs/AECS.js` lines 106–112

If `shutdown()` throws (e.g., `flushSuppressionSummaries` rejects), the exception propagates out of `await this.shutdown()`, but execution continues to `this.configure(options)` because there is no try/catch.

**Consequences:** Orphaned intervals, file handles, or in-memory state from the previous lifecycle.

**Recommended Direction:** Wrap `shutdown()` in try/catch and abort reinitialize on failure.

---

### 22.7 P2 — Medium: Unhandled Rejections in Analytics Flush (Systemic)

**Location:** `src/lib/analytics.js` lines 85, 92, 500

`void flushAll()` and `void flushRoleChanges()` are fire-and-forget. If these reject (e.g., SQLite lock errors), the rejection is unhandled.

**Consequences:** Bot process crash on analytics flush failure in Node.js >= 15.

**Recommended Direction:** Add `.catch(() => {})` or proper error propagation.

---

### 22.8 P2 — Medium: Zero Retry Logic for Webhook Delivery

**Location:** `src/lib/aecs/telemetry-adapter.js` lines 147–215

Every webhook delivery is a single HTTP POST with a 5-second timeout. No retry, no exponential backoff, no jitter.

**Consequences:** Under transient network failures, telemetry events are permanently lost.

**Recommended Direction:** Add retry with exponential backoff for 5xx and network errors.

---

### 22.9 P2 — Medium: Zero Retry Logic for File I/O

**Location:** `src/lib/aecs/vault.js` lines 263–326

File writes are fire-and-forget. `stream.write()` return value is not checked, ignoring backpressure. A single transient disk error permanently disables persistence.

**Consequences:** Single I/O error kills all local logging for the process lifetime.

**Recommended Direction:** Implement retry with backoff for file I/O. Handle stream backpressure.

---

### 22.10 P2 — Medium: suppressionMap Never Evicts Expired Entries

**Location:** `src/lib/aecs/Dispatcher.js` lines 92, 151–179

`shouldSuppress()` resets the counter when the window expires, but the fingerprint entry remains in `suppressionMap` forever.

**Consequences:** Memory leak proportional to unique error cardinality over process lifetime.

**Recommended Direction:** Delete entries when `windowStart` is reset, or run periodic cleanup.

### 22.11 P2 — Medium: Race Between shouldSuppress and flushSuppressionSummaries

**Location:** `src/lib/aecs/Dispatcher.js` lines 151–223

`shouldSuppress` mutates `state.count` and `state.suppressed` without any lock. `flushSuppressionSummaries` resets those same properties on a timer. If an error is dispatched while the flush is running, the count can be incremented after the reset.

**Consequences:** Suppression counts are unreliable. Errors may be over-suppressed or under-suppressed.

**Recommended Direction:** Use per-fingerprint mutex or atomic snapshot approach.

### 22.12 P2 — Medium: Stream Rotation Not Awaited

**Location:** `src/lib/aecs/vault.js` lines 231–261

When the date changes, old streams are `.end()`ed synchronously, but the actual buffer drain and file close happen asynchronously. New streams are opened immediately.

**Consequences:** Records written during stream rotation may be lost or partially written. JSONL and IDX files can become misaligned.

**Recommended Direction:** Await `stream.finished()` before opening new streams.

### 22.13 P2 — Medium: Config NaN Validation Missing

**Location:** `src/lib/aecs/AECS.js` lines 47–67

`Number.parseInt` on invalid input returns `NaN`. If `flushIntervalMs` is `NaN`, `setInterval` fires immediately and repeatedly. If `suppressionThreshold` is `NaN`, suppression is disabled.

**Consequences:** Config typos can cause infinite loops, unbounded memory growth, or disabled safety mechanisms.

**Recommended Direction:** Validate numeric configs after parsing; reject or clamp NaN values.

If `permissionsFor` throws or returns an object without `has`, the function returns `true` — meaning "yes, the bot has permission."

**Consequences:** Bot attempts to create webhooks in channels where it lacks permission, leading to API 403 errors that are silently swallowed.

### 23.1 P0 — Blocker: Two Divergent Recruit Implementations

**Location:** `src/commands/recruiting/recruit.js` (active, 652 lines) vs `src/services/recruiting/recruit-service.js` (inactive, 826 lines)

There are two completely separate implementations of the same recruit business logic. The active command uses raw SQL and lacks floor protection on points. The service layer has safer transaction handling and ledger integration.

**Key Behavioral Differences:**

| Aspect | Command (active) | Service (inactive) |
|---|---|---|
| Transaction | Raw `BEGIN TRANSACTION` (line 558) | `withTransaction()` — retries on SQLite busy |
| Multiplier fetch | Missing `guildId` (line 553) | With `guildId` (line 547) |

| Trial promotion | Uses `AUTO_PROMOTE_ROLE` | Uses `RECRUITER` + region role |
| Points update | Raw `UPDATE recruiters SET points = points + ?` | `changeRecruiterPoints` with floor/ceiling |

**Consequences:** Bug fixes applied to one path may not be applied to the other. The active command bypasses the ledger entirely.

**Recommended Direction:** Migrate active command to use the service layer, or consolidate into a single implementation.

## 24. Cross-System Interaction Analysis

### 24.1 Scheduler ↔ Anti-Nuke Interaction

The scheduler's `runWeeklyMondayReset` calls `performWeeklyRecalculations`, which internally calls `handleExpiredAbsences`. `handleExpiredAbsences` sends DMs to staff members. If the anti-nuke system is in a degraded state (e.g., missing audit log permission), the DM sends may still proceed, but the anti-nuke protection for those DM-related actions is absent.

**Risk:** Medium — DM sends are not protected by anti-nuke, but this is by design.

---

### 24.2 Recruit Flow ↔ Scheduler Interaction

The recruit flow resets weekly points inside `performWeeklyRecalculations` (line 167: `UPDATE recruiters SET points = 0`). This runs inside a per-recruiter transaction. If the scheduler is disabled (finding 20.3), the points reset never happens, causing points to accumulate indefinitely.

**Risk:** High — scheduler disablement causes silent points inflation.

---

### 24.3 Database Layer ↔ All Systems

The `void e` anti-pattern in db_async.js affects every system that relies on the database. Silent schema drift, missing indexes, and disabled foreign keys propagate silently into all business logic.

**Risk:** Systemic — every subsystem is affected by database layer issues.

---

### 24.4 Anti-Nuke ↔ Event Handlers Interaction

All event handlers (`guildBanAdd`, `channelDelete`, `roleDelete`, etc.) are registered without error boundaries. If any handler throws (e.g., due to finding 6.1), the entire event emitter chain for that event type is disrupted.

**Risk:** High — a single null dereference disables all protection for that event type.

---

### 24.5 DM Worker ↔ Database Interaction

The DM worker system uses `withTransaction(db, fn, { immediate: true })` which translates to `BEGIN IMMEDIATE`. This acquires a RESERVED lock on SQLite, serializing writers. However, the `txQueueByDb` WeakMap in `transactions.js` serializes transactions on the same db handle. If the DM worker and the main bot share the same SQLite connection, long-running DM transactions can block the main bot's database operations.

**Risk:** Medium — DM worker transactions can cause `SQLITE_BUSY` for the main bot under high DM volume.

---

### 24.6 AECS ↔ All Subsystems

AECS is initialized at module load time (index.js line 67) before any subsystem is ready. If AECS fails to initialize, the entire bot crashes. If AECS succeeds but its vault is disabled later (due to I/O error), all subsystems lose telemetry silently.

**Risk:** High — AECS is a single point of failure for observability.

---

### 24.7 Economy ↔ Scheduler Interaction

`getActiveMultiplier` is called from `recruit-service.js` during the recruit flow, but also from `scheduler.js` during weekly recalculations. If the scheduler runs `performWeeklyRecalculations` while a recruit is in progress, both may call `getActiveMultiplier` concurrently, causing the DELETE sweep to race.

**Risk:** Medium — multiplier purge race between recruit and scheduler.

---

### 24.8 Command Loader ↔ Register Commands Interaction

`command-loader.js` loads commands from files, while `register-commands.js` defines slash commands in hardcoded builders. If these get out of sync, the bot either:
- Loads a command that Discord doesn't know about (user sees "This interaction failed")
- Registers a command that has no implementation (TypeError when invoked)

**Risk:** High — deployment bug that is difficult to detect.

### 30.3 CORRECTED: Week Boundary Offset Mismatch

**Original Finding (Section 5.1):** Claimed that `scheduler.js:710` calls `getWeekStartUtcTs()` without offset while `weekly-recalculations.js:66` uses `WEEK_ROLLOVER_OFFSET_MS`, causing a mismatch.

**Verification:** This is **incorrect** as an active bug. Both call sites produce identical results because:

1. `getWeekStartUtcTs` always subtracts `DEFAULT_WEEK_OFFSET_MS` (5 min) from `now`
2. `scheduler.js:710` calls `getWeekStartUtcTs()` → subtracts 5 min from now
3. `weekly-recalculations.js:66` calls `getWeekStartUtcTs(new Date(Date.now() + WEEK_ROLLOVER_OFFSET_MS))` → adds 5 min, then subtracts default 5 min = net zero offset

Both produce the same `weekStart` value. However, this is a **latent maintenance hazard** — the two independent constants (`DEFAULT_WEEK_OFFSET_MS` in week.js and `WEEK_ROLLOVER_OFFSET_MS` in weekly-recalculations.js) cancel by coincidence. If either is modified independently, they will silently diverge.

**Severity correction:** The severity should be **LOW (P3)** for the current state (no active bug) and **CRITICAL (P0)** as a latent hazard that could be triggered by a well-intentioned refactor.

### 30.4 CORRECTED: ensureColumnWithRetry Error Handling

**Original Finding (Section 4.5):** Claimed that 26 `ensureColumnWithRetry` calls "swallow errors."

**Verification:** The `ensureColumnWithRetry` function (lines 1167-1187) actually has **proper error handling**:
- Catches "duplicate column name" and returns silently (correct idempotency)
- Logs non-transient errors at error level (line 1180)
- Rethrows non-transient errors (line 1181)
- Retries transient errors (database is locked, SQLITE_BUSY) up to 3 times with 500ms backoff
- Exhausts retries and rethrows (line 1183)

**Correction:** The 26 `ensureColumnWithRetry` calls are **redundant** (the columns already exist in the main schema block), but they do NOT swallow errors. However, their redundancy means:
1. 26 unnecessary ALTER TABLE attempts on every startup (always hitting "duplicate column name")
2. The retry logic kicks in for these expected errors, adding 500ms delays × 3 retries per call = up to 39 seconds of unnecessary startup delay on a cold DB (though typically the "duplicate column" check returns immediately)

**Severity correction:** Should be **LOW** for error handling (properly handled) but **MEDIUM** for the redundant startup cost and maintenance confusion.

### 32.2 CRITICAL: db-bootstrap.js PRAGMA Configuration Failures Silently Swallowed

**Severity:** HIGH
**Location:** `src/lib/db-bootstrap.js` lines 25, 32, 38, 39

```javascript
async function applyConnectionPragmas(db, env = process.env) {
  try { await db.exec('PRAGMA foreign_keys = ON'); } catch (e) { void e; }
  ...
  try { await db.exec(`PRAGMA journal_mode = ${journalModeRaw}`); } catch (e) { void e; }
  ...
  try { await db.exec('PRAGMA synchronous = NORMAL'); } catch (e) { void e; }
  try { await db.exec('PRAGMA busy_timeout = 10000'); } catch (e) { void e; }
}
```

**Root Cause:** All four PRAGMA settings are wrapped in try/catch with `void e`, silently discarding any failure. These PRAGMAs control critical database behavior:

1. `foreign_keys = ON` — If this fails, referential integrity is disabled for the entire SQLite session. Any cascading deletes or foreign key constraints are silently ignored.

2. `journal_mode = WAL` — If this fails, the database may fall back to DELETE journal mode, which doesn't support concurrent reads during writes. This can cause performance issues under load.

3. `synchronous = NORMAL` — If this fails, the default may be FULL (safe but slow) or OFF (fast but data loss risk). Unpredictable behavior.

4. `busy_timeout = 10000` — If this fails, SQLite will return SQLITE_BUSY immediately instead of waiting. This can cause spurious transaction failures.

**Consequences:**
- Data integrity violations (orphaned rows if FK constraints disabled)
- Performance degradation (if journal mode falls back to DELETE)
- Unpredictable durability (if synchronous falls back to OFF)
- Transaction failures (if busy_timeout not set)

**Reproduction Scenario:**
1. Start the bot with a read-only database file (or the `data/` directory doesn't exist)
2. `PRAGMA foreign_keys = ON` fails silently
3. Bot starts with FK constraints disabled
4. Orphaned rows accumulate in `recruits`, `warnings`, and other tables
5. No logging or alert indicates the problem

**Long-term Impact:** Silent data corruption. The bot will appear to work normally but silently accumulate referential integrity violations.

**Recommended Direction:** Log failures at warning level. For `foreign_keys`, log an error and exit if the PRAGMA cannot be set. For other PRAGMAs, log warnings but continue.

**Dependencies:** This issue is closely related to the systemic `void e` anti-pattern (Finding 30.2) and the `alter()` helper issue (Finding 30.1).

### 32.6 HIGH: Antinuke System Integration Layer Missing Error Boundaries

**Severity:** HIGH
**Location:** `src/lib/antinuke-system.js` lines 68-154

**Root Cause:** The `setupIntegration()` method monkey-patches 4 methods on `this.antiNuke`:

1. `handleRapidAction` (line 75)
2. `handleBeastModeTrigger` (line 97)
3. `handleEmergencyMode` (line 118)
4. `handleMassBanLockdown` (line 136)

Each patch:
1. Fetches the guild and member
2. Records pre-action state via rollback
3. Calls the original handler
4. Records post-action state via rollback

**Issues:**
1. **No error boundaries:** If `recordPreActionState` fails (e.g., DB locked), the error propagates to the event caller. If `originalHandleX` throws, `recordPostActionState` is never called, leaving the rollback state inconsistent.

2. **Partial failure state:** If `recordPreActionState` succeeds but `originalHandleX` fails, the rollback records the pre-state but never records that the action failed. The rollback system may attempt to restore a state that was never modified.

3. **Async race in monkey-patching:** The patches replace methods at runtime. If an event fires between the assignment of the original handler reference and the new handler (lines 74-75, 96-97, etc.), the wrong handler may be invoked.

4. **`this` binding issues:** The patches use `.bind(this.antiNuke)` but if `this.antiNuke` is replaced (e.g., during reinitialization), the bound methods still reference the old instance.

**Consequences:** Antinuke protection may fail silently during rollback state recording, leaving no ability to undo anti-nuke actions. A failure in rollback recording could cascade to anti-nuke action execution.

**Recommended Direction:** Wrap each patched handler in a try/catch. Ensure `recordPostActionState` is always called (even on error) with an `error` flag in metadata. Add circuit breaker to disable rollback recording if it fails repeatedly.

3. Does not handle `null` values (if `base[key]` is `null` and `value` is an object, `isPlainObject(null)` returns false, so `value` replaces `null` — this is correct, but not documented)

**Consequences:** Config files with arrays (e.g., `ROLES.STAFF = ["id1", "id2"]`) will have their arrays entirely replaced rather than merged, which is actually the desired behavior but is undocumented.

**Recommended Direction:** Document the merge behavior. Consider whether array replacement vs. concatenation is the desired default.

### 32.24 ADDITIONAL Finding: Transactions Module Serial Queue Has Race Condition

**Severity:** HIGH
**Location:** `src/lib/transactions.js` lines 56-73

**Root Cause:** The `withTransaction` function uses a `WeakMap` to serialize transactions on the same db handle. The pattern:

```javascript
const prev = txQueueByDb.get(handle) || Promise.resolve();
const run = (async () => {
    try { await prev; } catch (e) { ... }
    return executeTransaction(handle, fn, opts);
})();
txQueueByDb.set(handle, run);
```

**Issues:**
1. If `executeTransaction` fails (after `prev` resolves), the next transaction in queue will still proceed, even though the previous one failed. This could lead to data inconsistency.
2. The `finally` block at line 70 deletes the queue entry if it's the last one, but if a new transaction was queued during `finally`, it would never execute (race condition).
3. Errors from previous transactions are logged but swallowed, meaning downstream transactions may operate on inconsistent state.

**Consequences:** Under high DB load, transactions may execute on top of failed transactions, leading to data corruption.

**Recommended Direction:** Implement proper transaction queuing with error propagation. If a transaction fails, cancel all queued transactions for that handle.

### 32.25 ADDITIONAL Finding: Job-Locks Module Has Silent Fallback to Fail-Open

**Severity:** HIGH
**Location:** `src/lib/job-locks.js` lines 4, 26, 51

**Root Cause:** The `acquireJobLock` function returns `!!failOpen` on multiple error paths:

1. Line 4: If `db` or `guildId` or `key` is missing → returns `failOpen` (default `false`)
2. Line 26: If the primary acquire fails with non-transient error → returns `failOpen`
3. Line 51: If the fallback acquire also fails → returns `failOpen`

**Issues:**
1. `failOpen` defaults to `false`, meaning if the lock acquisition fails, the job does NOT run. This is actually correct for safety (fail-closed), but the parameter name `failOpen` is misleading.
2. If `failOpen` is set to `true` (as seen in some callers), a DB failure causes the scheduler to run without lock protection, potentially running jobs concurrently across multiple bot instances.

**Consequences:** If the database is temporarily unavailable, the scheduler either:
- Does not run scheduled jobs (if failOpen=false) — correct but silent
- Runs jobs without lock protection (if failOpen=true) — dangerous, may cause duplicate execution

**Recommended Direction:** Always use fail-closed (`failOpen=false`) for critical jobs. Log all lock acquisition failures. Implement retry logic for transient DB errors.
